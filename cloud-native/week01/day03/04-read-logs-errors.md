# 4교시 - 로그와 에러 메시지 읽기

## 목표

이 시간의 목표는 로그를 겁내지 않고 필요한 줄을 찾는 것이다. Day2에서 작은 웹앱의 요청 로그를 봤다면, 오늘은 여러 줄의 로그에서 시간, 수준, 경로, 원인을 분리해서 읽는다.

이 세션의 끝에서 우리는 다음을 할 수 있어야 한다.

- 로그 한 줄에서 시간, 수준, 메시지를 구분한다.
- `head`, `tail`, `grep`으로 필요한 로그를 찾는다.
- 에러 메시지를 질문 템플릿으로 바꾼다.

## 오늘 한 줄 요약

로그는 길게 읽는 글이 아니라, 증거를 찾기 위해 좁혀 보는 기록이다.

## 로그 한 줄 읽기

예시:

```text
2026-03-02T10:15:32Z INFO request method=GET path=/health status=200 duration_ms=4
```

| 부분 | 뜻 |
|---|---|
| `2026-03-02T10:15:32Z` | 언제 일어났는가 |
| `INFO` | 정보 수준 |
| `request` | 어떤 사건인가 |
| `method=GET` | 요청 방식 |
| `path=/health` | 요청 경로 |
| `status=200` | 응답 상태 |
| `duration_ms=4` | 걸린 시간 |

모든 로그가 같은 모양은 아니다. 하지만 시간, 수준, 사건, 상태를 나누어 찾으면 읽기 쉬워진다.

## 실습 - 로그 앞뒤 보기

`playground` 폴더에서 실행한다.

```bash
head logs/access.log
```

```bash
tail logs/access.log
```

마지막 5줄만 본다.

```bash
tail -n 5 logs/access.log
```

에러 로그를 본다.

```bash
cat logs/error.log
```

`ERROR`가 있는 줄만 본다.

```bash
grep "ERROR" logs/error.log
```

`/api/orders` 요청만 찾는다.

```bash
grep "/api/orders" logs/access.log
```

## 로그 수준

| 수준 | 흔한 의미 | 오늘의 판단 |
|---|---|---|
| `DEBUG` | 자세한 디버깅 정보 | 너무 많을 수 있음 |
| `INFO` | 정상적인 주요 사건 | 정상 흐름 확인 |
| `WARN` | 당장 실패는 아니지만 주의 | 원인 후보 |
| `ERROR` | 실패한 사건 | 먼저 확인 |

로그 수준은 절대적인 정답이 아니다. 서비스마다 기준이 다르다. 하지만 처음 볼 때는 `ERROR`, `WARN`, 최근 시간, 관련 경로 순서로 좁히면 된다.

## 에러를 질문으로 바꾸기

에러 예시:

```text
2026-03-02T10:20:04Z ERROR config missing required key DATABASE_URL
```

질문으로 바꾸면:

```text
제가 하려던 일: API 서비스 실행 준비
보인 증상: DATABASE_URL 설정이 없다는 ERROR 로그가 있음
이미 해본 것: logs/error.log에서 ERROR 줄 확인
궁금한 것: DATABASE_URL은 어느 설정 파일에 넣어야 하는지 알고 싶음
```

## 흔한 오해

- 로그 전체를 처음부터 끝까지 읽어야 한다고 생각한다. 실제로는 필요한 줄을 좁혀 본다.
- 에러 메시지를 복사하지 않고 “안 된다”고만 말한다. 에러 메시지는 가장 중요한 단서다.
- 마지막 줄만 본다. 마지막 줄이 원인일 수도 있지만, 그 전에 나온 설정 누락이나 권한 에러가 원인일 수 있다.

## 마무리 미션

다음 질문에 답한다.

1. `logs/error.log`에서 가장 먼저 확인할 줄은 무엇인가?
2. `/api/orders` 요청 중 실패한 요청은 몇 개 보이는가?
3. `DATABASE_URL`이라는 단어는 어느 파일에서 등장하는가?

힌트:

```bash
grep "DATABASE_URL" logs/error.log config/app.env
```
