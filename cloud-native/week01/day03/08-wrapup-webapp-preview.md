# 8교시 - 정리와 웹앱 구조 예고

## 목표

이 시간의 목표는 Day3에서 배운 터미널 생존법을 정리하고, Day4의 웹 애플리케이션 구조 학습으로 연결하는 것이다. 오늘 배운 명령은 Docker, Kubernetes, AWS에서도 계속 반복된다.

이 세션의 끝에서 우리는 다음을 할 수 있어야 한다.

- 터미널에서 길을 잃었을 때 복구 순서를 말한다.
- 로그와 설정 파일을 연결해 원인 후보를 설명한다.
- Day4에서 클라이언트, API, 데이터베이스, 설정, health check를 왜 배우는지 이해한다.

## 오늘의 생존 명령 10개

| 명령 | 한 줄 의미 |
|---|---|
| `pwd` | 현재 폴더를 본다 |
| `ls` | 파일과 폴더를 본다 |
| `cd` | 폴더를 이동한다 |
| `cat` | 파일 전체를 출력한다 |
| `head` | 파일 앞부분을 본다 |
| `tail` | 파일 뒷부분을 본다 |
| `grep` | 특정 단어가 있는 줄을 찾는다 |
| `find` | 조건에 맞는 파일을 찾는다 |
| `--help` | 명령 사용법을 본다 |
| `echo $?` | 직전 명령의 성공/실패 상태를 본다 |

Windows PowerShell에서는 일부 명령이 다르게 보일 수 있다. 하지만 이 과정에서는 WSL 또는 Linux 계열 터미널 기준으로 Docker/Kubernetes 실습을 진행하는 장면이 많다.

## 터미널 복구 순서

명령이 실패하면 아래 순서로 본다.

1. 현재 위치: `pwd`
2. 주변 파일: `ls`
3. 대상 파일 존재 여부: `ls <폴더>` 또는 `find`
4. 명령 도움말: `<명령> --help`
5. 에러 핵심 단어: `No such file`, `command not found`, `permission denied`, `connection refused`
6. 로그 확인: `tail`, `grep`
7. 질문 작성: 하려던 일, 보인 증상, 해본 것, 궁금한 것

복구할 때 삭제부터 하지 않는다. `rm -rf` 같은 명령은 원인 확인 도구가 아니라 삭제 도구다. 문제 해결 중 삭제가 필요해 보이면, 먼저 “무엇을 지우는지”, “현재 위치가 어디인지”, “되돌릴 수 있는지”를 확인한다.

## Day4로 이어지는 연결

오늘 `playground`에서 본 구조는 Day4 웹앱 구조의 축소판이다.

| 오늘 본 것 | Day4에서 연결되는 개념 |
|---|---|
| `apps/web` | 클라이언트 또는 웹 프론트 |
| `apps/api` | API 서버 |
| `config/app.env` | 설정과 환경 변수 |
| `logs/access.log` | 요청 로그 |
| `logs/error.log` | 에러 로그 |
| `DATABASE_URL` | 데이터베이스 연결 설정 |
| `/health` | health check |

Day4에서는 “파일이 어디 있나”를 넘어 “요청이 어느 구성요소를 지나가나”를 본다. Docker와 Kubernetes는 결국 이런 구성요소를 포장하고 실행하고 연결하는 도구다.

## 퇴실 미션

아래 incident note를 개인별로 완성한다.

```text
제목:
증상:
영향:
확인한 증거:
가능한 원인:
다음 확인:
```

조건:

- 증거는 최소 2개 이상 쓴다.
- 파일명 또는 명령을 1개 이상 포함한다.
- “잘 모르겠다”로 끝내지 않고 다음 확인을 적는다.
