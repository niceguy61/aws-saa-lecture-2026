# 1주차 4일차 - 웹 애플리케이션의 모양

## 목표

애플리케이션을 컨테이너로 포장하기 전에 클라이언트, API, 데이터, 설정, 상태 확인의 모양을 이해한다. Day2에서 작은 웹앱을 실행했고 Day3에서 로그와 파일을 읽었다면, Day4에서는 앱을 여러 부품으로 나누어 보고 실패 증상을 구조와 연결한다.

## 오늘 배울 내용

- 브라우저에서 앱까지 요청이 지나가는 흐름
- 클라이언트, API, 데이터, 정적 파일의 역할
- 설정과 health check가 필요한 이유
- 로컬에서 되는 앱이 배포에서 실패하는 이유
- 시연 앱의 증상으로 시스템을 읽는 방법

## 난이도 기준

첫 주는 비전공자도 따라올 수 있도록 용어를 풀어서 본다. 다만 오후 실습은 일부러 실패를 만들고 원인을 좁히므로, 모든 학생이 같은 속도로 끝내는 것을 목표로 하지 않는다.

| 수준 | 오늘의 목표 |
|---|---|
| 비전공/고등학생 | `/`, `/api/products`, `/health`가 서로 다르다는 것을 설명한다 |
| 대학생/부트캠프 수준 | 404, 500, unhealthy를 구분하고 증거를 찾는다 |
| 주니어 엔지니어 | 설정, 데이터, health check를 구조도와 진단 기록으로 연결한다 |

## 랩/미션/데모

오늘의 시연 앱:

- [demo_app](demo_app)

기본 실행:

```bash
cd cloud-native/week01/day04/demo_app
python3 server.py
```

Windows에서 필요하면:

```powershell
py server.py
```

브라우저 확인:

```text
http://localhost:8000
http://localhost:8000/api/products
http://localhost:8000/health
```

핵심 미션:

- `/`, `/api/products`, `/health`의 역할을 구분한다.
- 없는 경로를 요청해 404를 관찰한다.
- 데이터 파일 경로를 바꿔 500과 unhealthy를 관찰한다.
- 앱 구조도를 그리고 실패 지점을 표시한다.

## 실습 터미널 기준

오늘 자료의 명령은 Linux 계열 터미널 기준이다.

| 환경 | 권장 터미널 |
|---|---|
| Windows | WSL Ubuntu 터미널 또는 Git Bash |
| macOS | Terminal 또는 iTerm |
| Linux | 기본 Terminal |

Windows PowerShell용 명령은 필요한 곳에 따로 적어둔다.

## 오늘 나오는 핵심 용어

| 용어 | 쉬운 뜻 |
|---|---|
| client | 사용자가 보는 쪽 |
| API | 프로그램이 데이터를 요청하는 통로 |
| HTML | 브라우저가 화면을 그릴 때 읽는 문서 |
| JSON | 프로그램끼리 데이터를 주고받기 쉬운 형식 |
| static file | 그대로 전달되는 파일 |
| config | 환경마다 달라지는 설정값 |
| environment variable | 실행할 때 잠깐 전달하는 설정값 |
| health check | 앱 상태를 확인하는 약속된 경로 |
| `404` | 요청한 경로를 찾지 못함 |
| `500` | 서버가 요청 처리 중 실패함 |

## 오늘의 미싱링크 먼저 보기

오늘은 “웹 개발”을 깊게 배우는 날이 아니다. Cloud Native에서 계속 만나는 운영 질문을 작게 관찰하는 날이다.

| 헷갈릴 수 있는 질문 | 오늘의 답 |
|---|---|
| 왜 웹앱을 배우나? | 컨테이너와 Kubernetes가 실제로 실행하는 대상이 대부분 요청/응답 앱이기 때문이다 |
| 왜 API를 보나? | 화면 뒤에서 데이터가 어떻게 오가는지 알아야 장애를 설명할 수 있기 때문이다 |
| 왜 health check를 보나? | 화면이 떠도 운영 상태가 나쁠 수 있기 때문이다 |
| 왜 일부러 실패시키나? | 안전한 작은 실패를 봐야 실제 장애에서 당황하지 않는다 |
| 왜 구조도를 그리나? | 어느 부품이 실패했는지 말로만 설명하기 어렵기 때문이다 |

## Cloud Native 연결

Docker와 Kubernetes는 결국 이런 앱을 실행하고, 연결하고, 상태를 확인한다. 앱 구조를 모르면 컨테이너가 떠 있어도 왜 화면이 깨지는지, 왜 health check가 실패하는지 설명하기 어렵다.
