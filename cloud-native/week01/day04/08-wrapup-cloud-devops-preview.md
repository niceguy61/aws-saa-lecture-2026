# 8교시 - Day4 핵심 정리와 Live QA

## 목표

이 시간의 목표는 Day4에서 본 웹 애플리케이션 구조와 실패 증상을 다시 정리하고, 시연 앱 실행 중 생긴 질문을 Live QA로 해결하는 것이다.

이 세션의 끝에서 우리는 다음을 할 수 있어야 한다.

- `/`, `/api/products`, `/health`의 차이를 설명한다.
- client, API, data, config, health check의 역할을 구분한다.
- 404, 500, unhealthy, connection refused를 구분한다.
- 웹앱 구조도 위에 실패 지점을 표시한다.

## 오늘 한 줄 요약

Day4는 웹앱을 화면 하나로 보지 않고, 요청을 처리하는 여러 부품과 실패 증상으로 나누어 본 날이다.

## 반드시 알아야 할 키포인트

- `/`는 사람이 보는 HTML 화면이다.
- `/api/products`는 프로그램이 읽는 JSON 데이터 응답이다.
- `/health`는 앱의 운영 상태를 확인하는 경로다.
- `404`는 요청한 경로를 찾지 못한 것이다.
- `500`은 서버가 요청 처리 중 실패한 것이다.
- `unhealthy`는 앱이 응답하더라도 운영 상태가 좋지 않다는 신호다.
- config는 환경마다 달라지는 값이고, 코드와 분리하는 것이 중요하다.
- 구조도는 예쁜 그림이 아니라 장애를 설명하기 위한 지도다.

## 실패 증상 정리

| 증상 | 먼저 의심할 것 | 확인할 증거 |
|---|---|---|
| connection refused | 서버 프로세스가 꺼져 있거나 포트가 다름 | 서버 터미널, 포트 |
| 404 | 요청 경로가 없음 | URL 경로, 서버 로그 |
| 500 | 서버 내부 처리 실패 | 서버 로그, 데이터/설정 |
| unhealthy | 앱은 응답하지만 운영 상태가 나쁨 | `/health` reason |

`/api/products`가 500이고 `/health`가 unhealthy라면 서로 다른 문제가 아니라 같은 원인에서 나온 두 증상일 수 있다. 예를 들어 데이터 파일 경로가 틀리면 API도 실패하고 health check도 나빠진다.

## Live QA

남은 시간은 Day4 실습과 구조도 질문을 해결한다.

우선순위:

1. 시연 앱 실행 문제
2. 서버 터미널과 브라우저를 같이 보는 방법
3. 환경 변수 명령의 OS별 차이
4. 404, 500, unhealthy 해석
5. 웹앱 구조도에서 빠진 구성요소 찾기

질문할 때는 아래를 함께 가져온다.

```text
확인한 주소:
브라우저 응답:
서버 로그:
/health 결과:
최근 바꾼 설정:
```

## Day5로 이어지는 연결

Day5에서는 이 웹앱 구조를 Cloud와 DevOps 용어로 연결한다. 질문은 “앱이 보이는가?”에서 “이 앱을 다른 사람이 안정적으로 쓰게 하려면 무엇이 필요한가?”로 바뀐다.
